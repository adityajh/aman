Deepen: plan and tracker

Status, architecture, decisions, roadmap, backlog and changelog for Deepen, outcome tracking for solo counsellors.

Overview

Deepen is practice software for counsellors in India who work alone. It handles the admin (sessions, notes, monthly invoices, payments) and, more importantly, tells a counsellor privately whether their clients are getting better. The product works and is in daily use by one practice. The work now is turning it into a business.

This page keeps the live status, the architecture, the decisions, the roadmap, the backlog and the changelog in one place, so that the next person or agent to pick Deepen up does not have to rebuild it from commit messages and chat.

The three jobs this page does

  • What to do next. The roadmap and backlog, with what is blocked and on what.
  • Where things stand. Live status of production, the practices on it and the open risks, read from the systems, not estimated.
  • Context for somebody new. Enough architecture to make a safe change on day one, including the traps that have already caught people.

The rules that matter most

There is one database, and it is production. Local development and every Vercel preview deployment point at the same live Neon database as the real site. Anything you run that writes, writes to real practices' data.

Every tenant-scoped query goes through withTenantContext() (src/lib/tenant.ts), which switches to a restricted role and sets the tenant for row-level security. A leak here is a clinical-data breach. The tenants, users and promo_codes tables have no row-level security, so any query on them must filter by tenant ID itself (see Architecture).

Ask Adi before anything irreversible: a schema change, a data write, a push or merge to main, a message to a real person.

Architecture

What the system is, and the mechanisms that are not obvious from reading the code in file order.

The stack

Next.js 16 App Router, React 19, TypeScript, Drizzle ORM on Neon Postgres, NextAuth v4 with email and password, Tailwind and shadcn/ui, hosted on Vercel. Three things differ from what you may expect:

  • The middleware file is still src/middleware.ts. Next 16 warns that the convention is now proxy.ts; it has not been renamed.
  • Route context params are async: await params, not params.
  • next.config.ts sets typescript.ignoreBuildErrors: true, so a type error does not fail the deploy. npx tsc --noEmit currently reports zero errors; keep it that way by running it yourself.

Tenant isolation

Every practice is a row in tenants. Every clinical and money table carries tenant_id, with row-level security enforced and one policy each: tenant_id = current_setting('app.current_tenant_id').

withTenantContext(tenantId, fn) opens a transaction, runs SET LOCAL ROLE authenticated (a role without BYPASSRLS) and sets the tenant. Inside it, a query that forgets its WHERE tenant_id is still scoped. That is the point.

tenants, users and promo_codes have no row-level security. A query on them inside withTenantContext is not scoped. tx.query.tenants.findFirst() with no where returned whichever practice Postgres listed first; four places did exactly that until 17 Nov 2026 (CHANGELOG 5.0.8). Always filter these tables by ID yourself.

Login, signup, admin and the Razorpay webhook use a second connection (db, the HTTP driver) with no tenant context at all. Code using db must scope by hand.

The pool has no error handler. When Neon closes an idle connection the error is unhandled and logged with the whole client config, which is how the database password reached Vercel's logs.

Money

The rules that are load-bearing:

  • Pro-rata billing by 15-minute quartile of actual time, with a 53 to 70 minute band billed as a standard hour. Manual fee overrides are never recalculated.
  • Invoice numbers are MAX(suffix) + 1 per tenant per year. Never count + 1; that once produced duplicates (CHANGELOG 3.5.1).
  • Receipts are the client-facing payment record; payments rows are allocations of a receipt across invoices, oldest first. Receipt numbers are currently computed across all tenants, not per tenant (see Backlog).
  • INR and USD are never summed together, anywhere.
  • Bank and UPI details on invoices come from each practice's own settings (CHANGELOG 5.0.9). The block is left out if a practice has entered neither.

Time

All wall-clock times are IST via src/lib/tz.ts, whatever the server's zone. Every date range is closed-open, [start, end).

Email

All app email (invoices, receipts, reminders, progress charts) goes out over Gmail SMTP as one personal Gmail account, set in Vercel as SMTP_USER. The sender name shows the practice; the account is the same for every practice. Resend is installed and keyed in Vercel but unused. deepen.health now has working mail (Hostinger, SPF, DKIM, DMARC), so moving to it is unblocked.

Settings has a Test Mode (practice_settings.email_override) that redirects a practice's client emails to the counsellor. Use it for any test of a send path.

Schema changes

Drizzle's migration journal lists only 0000 to 0004, and the live database's drizzle.__drizzle_migrations table is empty. Everything since was applied by hand. Do not run drizzle-kit push or migrate against production.

One-off SQL goes in drizzle/manual/, is reviewed by Adi, and runs once. Write it additive and idempotent (ADD COLUMN IF NOT EXISTS). Apply it before pushing code that needs it: Drizzle selects every column it knows about, so new code against an old schema fails on that table.

Deploys

Every push builds on Vercel, and preview deployments use the production database. Never push a branch whose code needs a schema change that has not been applied: the preview breaks, and anyone who opens it writes to live data.

Running it from a cloud session

The cloud environment "Deepen" holds the connection string as AMAN_DATABASE_URL and allows the database hosts. Two things are needed:

  • NODE_USE_ENV_PROXY=1, for the HTTP driver.
  • A preload shim that tunnels tls.connect to *.neon.tech through the HTTPS proxy, for the WebSocket pool, which ignores proxy settings. It lives in the session scratchpad and has to be recreated each session.

DD-01: Never sell to organisations

Not to platforms, employers or startups. The same outcome feature that helps a counsellor who chose it harms one who has it imposed by an employer. No supervisor view, no rankings, no badges. Reasoning in business/strategy/03-business-strategy.md sections 3 and 3.5.

DD-02: The never-build list

Scheduling, telehealth, booking pages, insurance, directories, AI note drafting, GST, expense management, clinic management, badges, gamification. When someone asks, the answer is a link to the list, not a roadmap conversation.

DD-03: Pricing

One plan at ₹999 a month with a 40 monthly-active-client soft limit; the founding 50 at ₹699 for 12 cycles, then ₹999; Pro at ₹1,999 later, gated by the PRACTICE_OUTCOMES flag. Decision of 17 Aug 2026 in business/commercial/pricing-and-build-plan-2026-08.md. The client limit was broadened to monthly active clients on 28 Oct 2026 (CHANGELOG 5.0.7).

DD-04: The measures position

Deepen records ORS and SRS scores a counsellor collected on paper under their own licence. It does not supply or administer the instruments. The licence offered was not signed, because it would cost the benchmark pool permanently. The one real exposure is eight item labels copied into the note editor; fixing them is lawyer-gated. Canonical statement: business/commercial/2026-08-31-measures-position.md.

DD-05: Online payments

Each counsellor connects their own Razorpay account by OAuth. Money goes from the client to the counsellor's Razorpay to their bank. Deepen never holds funds, which keeps it outside RBI payment-aggregator rules. Receipts go out automatically by default; INR only for now. Built on feat/razorpay-connect-payment-links, not yet run against Razorpay.

DD-06: Cold outreach

The operating plan of July ruled cold outreach out. Adi reversed that on 22 Nov 2026. Campaigns send from Hostinger mailboxes on outreach.deepen.health so complaints attach to the subdomain, not to the domain the app's invoices will use. Replies and one-to-one mail go to adi@deepen.health. Never send a campaign from an @deepen.health address. business/strategy/07-operating-plan.md section 3.2 still lists cold outreach as ruled out and needs updating.

DD-07: Bank details per practice

Until 17 Nov 2026 every practice's invoices printed one hardcoded bank account. Now five optional settings columns hold each practice's own details, and the original practice's details were moved into its own settings.

DD-08: Free accounts

Two ways exist: the promo code FREEBIE at signup, and creating the account by hand. Both make a billing-exempt tenant with no client limit and no expiry. There is no automatic trial end. FREEBIE is hardcoded and reusable by anyone who learns it. Open: whether to replace it with single-use codes from /admin.

DD-09: How this page is kept

Repo markdown plus a generated page, the same arrangement as the Outreach Orchestrator, so it is reviewed in diffs and checked for drift rather than edited in a wiki nobody checks.

  3. Correct "Hosted in India". Home, privacy and terms pages. The database is in AWS us-east-1.

  5. Make the subscription webhook reachable and signed. Exclude /api/webhooks in the middleware and refuse unsigned calls, in one change. Fixing only the first opens an unsigned endpoint.

  1. Strip instrument names from public copy, and the measures fix. Group A of HANDOVER-measures-AB-2026-08-31.md after lawyer review of the A1 wording; group B alongside.

  3. Automated measure delivery, on PHQ-9 and GAD-7. The highest-value unbuilt thing; without it the counsellor types every score by hand.
  4. The Outcome Report. The artefact a counsellor can use as evidence of their own effectiveness.
  5. Benchmark pool, with opt-in consent. The only compounding moat.
